# Tranche 0.4 — every repo path that can reach `ep-odd-fog`

**REPORT ONLY. Nothing in this file was implemented.** The proposal in §3 is a design with a
cost estimate, for the owner to accept or reject. No guard was added, changed, or removed on
the strength of it.

Method: `rg` over the repo for `ep-odd-fog`, `DATABASE_URL`, `new pg.Client`, `new pg.Pool`,
`neonctl`, plus reading `scripts/lib/target-guard.mjs`, `scripts/lib/neon-connection.mjs`,
`scripts/lib/neon-branch-guard.mjs`, `scripts/assert-ingest-env-dev.mjs`, `deploy.sh`, and
`web/src/lib/db.ts`. Production means the Neon endpoint `ep-odd-fog` in project
`spring-heart-74819093`, by any route.

## 2. What the current design actually enforces

The guards are strong **per script** and absent **per connection**. `target-guard.mjs` is
imported by the scripts that remember to import it. There is no point through which a
connection to `ep-odd-fog` must pass, so the enforcement surface is "every current and future
file that opens a socket", which is exactly the surface that produced the drift its own header
documents (four hand-copied copies, two fail-open).

Concretely: **C1 cannot be closed by anything in this repository.** Any mechanism proposed
below is a mechanism for the A/B/D doors, and honesty requires saying so up front rather than
implying `node -e` has been dealt with.

---

## 3. Proposal — ONE fail-closed mechanism

**A single chokepoint module, enforced by a static test, plus an environment-level refusal for
the door the static test cannot see.**

### 3a. The chokepoint

`scripts/lib/db-open.mjs` exporting `openDb({ url, intent, declared })` as the **only** place in
the repo that constructs `new pg.Client` / `new pg.Pool`. It:

1. resolves the endpoint id via `target-guard.endpointId`;
2. requires `intent` ∈ `read-only` | `write` | `ddl`, stated by the caller at the call site;
3. for `ep-odd-fog`: refuses unless `intent === 'read-only'` **and** `PROD_READ_OK=<endpoint id>`
   **and** `--target`/`declared` names it exactly — then issues `BEGIN; SET TRANSACTION READ ONLY`
   and asserts `transaction_read_only` and `current_user` at the server before returning,
   registering a `ROLLBACK` on close (i.e. A1's behaviour, made unavoidable rather than
   re-implemented per script);
4. refuses `intent: 'write' | 'ddl'` against prod outright — writes go through `cutover.mjs`,
   which would take the same door with its own override;
5. logs one line naming endpoint, intent, role. No credentials.

Fail-closed: an endpoint it does not recognise is refused, not admitted.

### 3b. The enforcement

A standing test — same shape as `test/prod-path-no-transpiler.test.ts` — that greps the repo for
`new pg.Client` / `new pg.Pool` / `postgres(` outside `scripts/lib/db-open.mjs` and fails with
the offending paths listed. Its own red-proof: add a raw client to any script, watch it go red.
Without this test the module is a convention; with it, it is a rail.

### 3c. The door 3b cannot see

For C1/C2, the only fail-closed control is **at Neon, not in git**: production's `app_runtime`
role restricted to `SELECT`, with writes reachable only through a separate role whose credential
is not in any developer environment. Then a stray `node -e` against prod is *incapable* of
writing rather than merely discouraged. This is an owner action, not a repo change.

### 3d. Cost

| Item | Estimate |
|---|---|
| `db-open.mjs` + types + its own red-proof | ~1 day |
| Migrating the ~45 call sites in `scripts/` + `src/ingest/` | ~2–3 days, mechanical but wide; every one needs its `intent` chosen by a human who knows whether that script writes |
| The `new pg.Client` static test + red-proof | ~2 hours |
| Churn risk | High-touch across ingest and cutover. Should land on its own branch, not inside a work order that also changes behaviour. Rollback is `git revert` — no data risk, since the change only narrows what is permitted |
| 3c (Neon role split) | Owner + a rehearsal on a fork; not estimable from here |

**Recommended sequencing:** 3b first, alone. The static test can land in hours and immediately
tells you the true call-site count instead of the ~45 estimated here by grep. Building 3a before
that number is known is guessing.

---

## 4. Residual, stated plainly

Even with all of the above: **A1's `--target` is still one word.** The mechanism moves the
decision from "did this script's author remember a guard" to "did the operator type an endpoint
id and set an env var", which is better but is not a technical impossibility of touching
production. The only control that makes prod writes *impossible* from a developer machine is
3c, and it is not a repo change.
