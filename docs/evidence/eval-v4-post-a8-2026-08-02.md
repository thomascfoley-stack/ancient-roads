## Read this before citing any of it

**Every movement here is ONE QUERY, and none of it should be read as an effect.** Pericope is
n=15, so 80 → 73 is a single question changing answer (6.7 points per query). Proper-noun is n=10,
so 60 → 70 is also a single question (10 points per query). Topical HIT@1 80 → 75 is one query at
n=20. **No causal claim about the patristics is supported by these deltas**, in either direction,
and the design doc already warns that topical and pericope CIs straddle their bars at this n.

What the run DOES establish, which is what it was for: adding 18,371 sections to the composed pool
**broke nothing**. No bar fell below its line, controls stayed clean 10/10 with zero hijacks, and
no category returned empty.

The v4 caveats in `HELDOUT_EVAL_DESIGN.md` all still apply and are not re-litigated by this run:
26% of v4's ground-truth labels also appear in v3; v4's KJV-phrase-anchored style is easier than
v3's abstract queries, so the abstract-topical failure mode is not exercised; and v4 samples no
Song of Solomon, so the known SoS hole is not covered by `no-content = 0`.

**Two topical queries returned a wrong answer** (`18 pass / 2 wrong`). They are not tuned against
— per the design doc's verdict logic, misses are failure-coded and reported, never fixed toward
the test.

## Two defects in the eval harness, found by running it

Both were unchecked HTTP responses, and the second is the first one's twin.

1. **`embed()` indexed `.data[0]` on the provider's error body.** A 401 surfaced as
   `Cannot read properties of undefined (reading '0')` — which reads as a bug in the eval and
   actually means the key is wrong. Fixed at `87bf053`.
2. **`rerankAll()` had the identical defect, in the function directly below**, and survived the
   first fix because only one of the pair was changed. It fired **100 queries into a 120-query
   run**, throwing away a full eval's worth of API spend with no indication of the cause. It now
   checks the response AND retries bounded on 429/500/502/503/504 — MASTER.md's watchlist already
   records an unearned RED from this exact provider returning 429 `engine_overloaded`, and a
   frozen eval dying at query 100 on a transient is that same failure with a bigger bill. A 401
   still fails immediately: no amount of waiting fixes a wrong key.
