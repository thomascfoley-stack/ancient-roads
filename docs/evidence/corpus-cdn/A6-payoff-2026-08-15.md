# A6 — the payoff, measured honestly (not from the CLI's progress bar)

## The problem with the obvious number

The `vercel --prod --archive=tgz` deploys today (`ca2eb2b`, `5e24cd8`) all printed the SAME
upload total: `(358.2MB/358.2MB)`. Taking that at face value would have said the
`.vercelignore` payoff (excluding `bible/`, `commentaries/`, `original/` — see `5e24cd8`) did
nothing. **It is a display artifact, not a byte count**, proven three ways:

1. Ran a non-prod preview deploy with `--debug`. The client-side scan correctly reported
   **736 files** included after applying `.vercelignore` (26 rules) — matching a from-scratch
   walk of the tree with the `ignore` npm package (734 files; the CLI counts 2 more, likely
   root config files it never ignores).
2. That tiny file set packed into 4 tarball chunks, of which only 4 needed fresh upload
   (`"Total files 4, 4 changed"` — the rest were already cached server-side from earlier deploys
   today). Four chunks of a ~11MB tarball cannot plausibly be 89.5MB each.
3. The progress bar's climb was in exact quarters — 0 → 89.5 → 179.1 → 268.6 → 358.2 — i.e.
   `358.2 / 4 = 89.5`. It was dividing a STALE total evenly across however many chunks existed
   this run, not measuring bytes in flight. The number never updates between runs; it lagged
   from the pre-CDN baseline.

## The real measurement

Built the exact archive the CLI would build — same file-collection logic (`ignore` matching
against `web/.vercelignore`, gzip-compressed tar — both independently reproduced, source at
`scripts/` is NOT committed, this was a one-off diagnostic):

| | file count | compressed size |
|---|---|---|
| **OLD** `.vercelignore` (per-chapter Bible excluded only) | 4,324 | **353.8 MB** |
| **NEW** `.vercelignore` (bible/commentaries/original fully excluded) | 734 | **11.5 MB** |

**Reduction: 342.3 MB, 97.2% smaller, 3,590 fewer files.** The OLD number (353.8MB) is close
enough to the CLI's own historical `358.2MB` (a ~1.2% gap, consistent with gzip-level
differences between my `tar -cz` and Vercel's packer) to trust both measurements are real for
the file set each was computed against — the baseline was genuine, and the CLI simply never
recomputed its displayed total for the smaller upload.

## What this does NOT change

The deployed bundle really is ~11.5MB of source now (matching the file-count evidence from the
live debug log, not just the disconnected reconstruction) — `ca2eb2b` and `5e24cd8` are both
live on production, both verified by `alias_serves == deployment_id`, and `5e24cd8` is the one
serving `ancientpaths.app` as of this writing. The corpus itself continues to be served
correctly via `CORPUS_CDN_BASE` rewrites to the Blob store (parity-proven, 200 sampled fetches
hash-verified). Nothing about this correction touches whether the site works — it only
corrects what number to report as the deploy-size payoff.

## Worth carrying into the watchlist

An instrument reported a number that looked live (a filling progress bar, ending at "N/N") but
was computing its own total from stale/cached data rather than the current run — the same shape
as `MASTER.md`'s "an instrument's blind spot recorded as a property of the thing it could not
see." The tell here was the SAME instinct that catches it elsewhere: the number didn't move
when the input plainly should have moved it, three deploys in a row.
