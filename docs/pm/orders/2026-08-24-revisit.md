## B. Deferred, with cost and trigger

### D10 — no incremental embedding progress
**Deferred in full, not half-fixed.** Both mitigations the memo floated fail on inspection:
- Exporting `maxDuration` on the upload route is a **documented decision with a guard**:
  `ask-max-duration-literal.test.ts` holds every `maxDuration` under `web/src/app` equal to
  `ASK_MAX_DURATION_SEC`, because for the ask routes the ceiling and the in-process budget are one
  number. Parsing has no such relationship, and adding a third consumer with unrelated semantics
  makes that guard mean less.
- Capping `drain(max)` does not bound the actual failure, which is **one** large document's embed
  phase outliving the function and restarting from batch zero.

**Cost to do properly:** persist embeddings per batch so a claim is resumable, or bound each
invocation to a slice and re-queue the remainder. Real work in the queue's core.
**What would size it:** the deployment's actual `maxDuration`, which cannot be read from the tree.
**What would change the call:** a user actually failing to ingest a large PDF. D9's fix now makes
that failure honest instead of a double-spend loop, which is why this can wait.

### D4 half B — the Romans doxology cannot be cited
**Measured, precisely.** WEB places the doxology at 14:24-26; the corpus, commentary metadata and
user anchors are KJV-keyed at 16:25-27. Across all 1,189 chapters, WEB's verse count differs from
KJV in exactly **two**: Rom 14 (23→26) and Rom 16 (27→25). This is one passage, not a systemic
versification problem. 16 commentary entries sit at 16:26-27, i.e. at numbers `verseExists`
rejects. A natural composition burns a compose attempt on a deterministic `passage_exists`
rejection; worst case is fallback, floor is a wasted attempt.

Half A (the guarantee half — empty verses passing the verifier) **is fixed** (`36240ac`).

**Cost to do properly:** either reconcile `web/public/bible/web/rom.json` with upstream WEB, or
make `verseExists`/`passage_exists` versification-aware instead of assuming KJV≡WEB. Both touch
served Bible data and want a re-verified asset.
**What would change the call:** a second translation diverging, which would turn a one-passage
patch into a real versification layer.
**Related, and NOT D4:** a scan of all 162,371 commentary entries found **2,134** whose verse range
exceeds the chapter's length. Only ~16 are the Romans issue; the rest are prose works mis-anchored
past chapter end in chapters where WEB and KJV agree (e.g. `psa 1`, 6 verses, carrying 28 entries
at verse 21). Separate finding, unfiled until now.

### D6 — the backfill for the 14,346 dropped entries
The key is fixed going forward (`8e7bdec`) and is now injective: **0 collisions** across the corpus.
Rows already written keep their legacy ids.

**Cost to do properly:** every legacy `source_id` changes, so this is a full re-embed of the flat
corpus. Worse, `ON CONFLICT DO NOTHING` means a naive re-run **inserts alongside** the old rows
rather than updating them — the migration has to delete-then-write or map old→new. Anything that
stored a `source_id` (study clippings via `study_blocks.source_id`, saved threads) needs migrating
or tombstoning.
**What would size it:** a production count of `source_id`s whose rows disagree on `sourceTitle`.
That is one query and it is owner-gated.
**Residual while it waits:** a clipping taken with no explicit `chunkIndex` resolves
`ORDER BY chunk_index LIMIT 1` and can land on the other work's chunk under a collision. Quote and
attribution stay mutually consistent — this is not misattribution — but it may not be the passage
the reader chose.

## E. Questions I would have asked, with the answer I chose

1. **D49 — "make the delete route honest" reads like: return 404 when nothing was deleted.**
   I did not. The 204-always is a documented anti-enumeration decision in the route's own words
   ("there is then NO existence oracle at all"), and a 404-vs-204 split hands any caller a
   does-this-id-exist-and-is-it-mine probe — the same oracle class this sweep closed on sign-up.
   **Chose:** fix the STORE so 204 becomes true, leave the route alone. Rule 1.

2. **D5 — the sweep offered "skip anchor-range grounding when the section has no real anchor".**
   That turns a fail-closed into a fail-open: a fabricated anchor on an unanchored source would
   stop being rejected. **Chose:** fix only the recoverable case (a real `verseId` with a missing
   or inverted `verseEnd`) and add a test pinning that a fully unanchored row still rejects
   everything. Rule 1.

3. **D6 — I graded it an attribution defect last session. It is not.**
   `getSource` takes the retrieval index, not a DB `source_id`, and every consumer that touches a
   real `source_id` takes quote and attribution from the same row. **Chose:** correct the record in
   the commit message and grade it as content loss plus an ambiguous key. Rule 2, applied to my own
   prior work.

4. **D25 — is the publish flag or the quarantine check the fix?**
   Both, independently. A quarantined entry with no `serve` key computes `publish: true` under the
   sibling formula too — that is the `chesterton-preexistence` shape. Fixing one leaves the other
   open. **Chose:** both, plus an invariant over every adapter rather than the one that was broken.

5. **D23 — is it reachable now that ADR-120 deleted the patristic producer?**
   Yes. `ingest-commentary-api` still fills `data/commentaries-api` over the network with no local
   prerequisite, and `predeploy-gate.ts:180` tells the operator to run the destructive script at
   exactly the moment the corpus needs rebuilding. **Chose:** fix it, and preserve register-owned
   entries unconditionally rather than by author name, because author-keying is one normalisation
   away from deleting a register work and the tree has no git backup.

6. **Sweeping D43 across 14 more route files — scope creep?**
   The finding is "an auth outage reports as signed out app-wide". Fixing five routes leaves the
   finding open. **Chose:** sweep all 24 call sites, but only catch blocks whose sole action was the
   bare response, so nothing doing real work was touched.

### Blocker 1 — `PREDEPLOY_DB_URL` (mine to report, yours to supply)
The bundle queries `embeddings.served` (migration 044). Deploying without proving that column
exists on the TARGET database 500s every `/ask`, so the gate refuses. It wants a read-capable URL
for **production**.

There is no production URL anywhere I can legitimately reach: not in the shell, not in
`.env.local` or `web/.env.local` in either tree. The only place it exists is Vercel's env store,
and the only way to get it is `vercel env pull`, which **writes a production connection string to
disk** — which `AGENTS.md` forbids in as many words. I did not do it, and I did not fabricate a
URL to get past the gate. **I stopped here.**

To finish: `PREDEPLOY_DB_URL='<prod pooled read URL>' ./deploy.sh` from a clean checkout of this
branch.

### Blocker 2 — the Vercel project's `rootDirectory` (a third session's change, unruled)
Reported by the peer session and **partially verified by me**: `deploy.sh` runs every vercel call
from `$REPO_ROOT/web` (line 248, with a comment saying this matches every successful deploy in
`docs/evidence/deploys`, and `test/deploy-sh-gates.sh` asserts it). The peer measured the project's
`rootDirectory` as `"web"`, set by a third session so GitHub builds could find the Next app. If

**I could not confirm `rootDirectory` myself** — the Vercel MCP's `get_project` does not return

CLI deploys need `"./"`, git builds need `"web"`. They are mutually exclusive, two sessions have
